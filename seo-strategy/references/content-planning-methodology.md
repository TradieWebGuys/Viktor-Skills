# Content Planning Methodology

Governs what content gets produced, in what order, and at what pace under the SEO AEO 2.0 program. Extends Section 3 of the Program Overview.

---

## 1. Content sequencing

Sequencing happens at two levels: a one-time foundation gate per client, then continuous block production once foundation clears.

**Foundation gate.** No content is produced until foundation work is signed off. Length depends on entry path, and it is never shortened to hit a content quota:

- **New client, not previous TWG website build** — ~4 weeks. If no website exists: discovery, sitemap/IA planning, matrix mapping (services × real service suburbs) before any page is designed, with core page copy (home, about, contact, primary services) written as part of the build itself — not counted toward the content cadence. If a site already exists: full technical/content/backlink/GBP audit, including a specific check for thin, duplicate, or cannibalising pages inherited from a prior agency or DIY effort, matrix-mapped against what already exists so the gap analysis reflects reality. Either way, once the site is live/fixed, it enters the same ramp (below).
- **Website built by TWG in last 5 years** — ~2 weeks: internal-only health check — confirm schema and tracking are still correct, GBP health check, matrix gap-check against what's been built since launch. No external audit needed since the build is already known.

GBP posting starts week 1 for every path, independent of foundation or content status — Mon/Wed/Fri, and not limited to the current block's pillar service; posts can cover any service angle the business offers.

**Ramp period.** Neither track starts at full cadence on day one — that's earned once foundation work de-risks the domain:

| Path | Weeks 1–4 | Weeks 5–6 | Weeks 7–8 | Full pace reached |
|---|---|---|---|---|
| New client, not previous TWG website build | Build, or audit + fix pass — no content | 1/week — new build: highest-intent location pages first. Existing site: priority to rewriting existing weak pages over new ones | 1–2/week — mix shifts toward new location pages | Month 3 (new build); month 3–4, audit-dependent (existing site) |
| Website built by TWG in last 5 years | Weeks 1–2: health check only | 2/week from week 3 — full engine, no throttling needed | 2/week | Month 2 |

**Steady state.** Content moves in 3-month blocks — one pillar page, its location-page variants, and supporting content, all drawn from a single service cluster. New pages, location pages, and blog content aren't prioritised against each other within a block; the mix is set by whatever the monthly strategy review flags as the gap. The one exception is the very first block of an engagement, where there's no ranking/decay data yet to base that on — defaulting to location pages first there is reasonable since it's the highest local-intent lever and fastest to show movement, but that bias shouldn't carry into later blocks once real data exists to reallocate from.

## 2. Content velocity

Fixed at 2 pieces/week (~8/month) for new content, same rate regardless of block. New service pages, location pages, and blog content are all counted as "pieces" within this rate — there is no separate blog-only quota sitting outside it.

Rewrites run on a separate track and are not counted against the 2/week new-content rate. Early in an engagement — particularly on a legacy site carrying thin or spun pages — rewrite output can exceed 2/week, since it touches pages already indexed rather than spending new crawl trust on the domain. Track rewrite output as its own line, not folded into the new-content count.

## 3. Seasonal planning

Handled through normal block assignment rather than a separate seasonal rule. Blocks run on a 3-month cycle and the next block is assigned at the monthly review that closes out the current one — that cadence is short enough for seasonal timing to be a normal input into commercial-value sequencing rather than needing its own override: a hot-water cluster due to peak in winter gets assigned to the block that lands ahead of that window as part of ordinary planning.

## 4. New page vs. rewrite

- **Rewrite in place** if the existing page has any organic traffic, ranks for any target keyword — even beyond page 1 — or has inbound links. This preserves existing equity and addresses the core risk directly: a weak page left in place drags the whole domain down.
- **New page** if the target page doesn't exist, or the existing one has none of the above and the structural problem — wrong keyword baked into the URL, wrong page type — is the actual issue.
- **Consolidate and redirect** if multiple existing thin pages compete for the same target keyword.

This applies both at onboarding (the existing-site audit prioritises rewrite/prune over new pages in the first content weeks) and on an ongoing basis — the monthly strategy review reallocates the block mix based on what ranked, stalled, or decayed, and any flagged page goes through this same rewrite/new/consolidate decision. Rewrite work should be tracked as its own line item rather than folded into new-content counts, so it doesn't get silently dropped once production ramps up — the refresh work is often what unlocks a site's ability to rank at all.
